what's left (the actual product)
--------------------------------
this is the part that scares me tbh. right now it's a key-value cache with an http api. the README says "llm gateway" and that's... not true yet.

[ ] no llm proxy at all. nothing forwards to openai / anthropic / anyone
[ ] no semantic cache. /similarity is just a math endpoint sitting alone, nothing embeds prompts or checks "have i answered something close to this before"
[ ] /stream is 3 hardcoded lines, not real streaming
[ ] no real token counting (no tokenizer)
[ ] no ttl on the lru cache. redis has set_ttl but the backend doesn't expose it
[ ] no auth, no rate limiting, no config file
[ ] no real server tests. only curl calls in ci
[ ] README oversells everything (asan/tsan/valgrind "clean", windows ci, runtime dispatch). need to tone it down or make it true


where i'm struggling
--------------------
1. ci / cmake hell
   burned like 20 commits thinking it was the cmake version. it wasn't. it was google-benchmark trying to download googletest. the error message pointed me the wrong way and i kept guessing instead of reading the log properly.
   lesson: read the actual failing line before touching anything.

2. i can't build on my own machine
   no c++ compiler on my windows box. everything goes through a docker ubuntu container or ci. every check = minutes of waiting. slow feedback loop = i guess more and verify less.
   maybe: install msvc build tools or wsl so i can build locally.

3. stuff that "works" but was never actually run
   the README says tests pass, sanitizers clean etc but ci never got past configure. so none of it was ever checked. redis code never compiled. docker image never built. finding this out one layer at a time is kinda demoralizing ngl.

4. redis + concurrency stuff
   connection pool, reaper thread, locks, condition variables. this is where the subtle bugs live (the reaper blocking stop() for 10s, moving an object a thread still points at, tests racing each other under ctest -j). hard to see just by reading the code, and it only shows up under parallel runs.

5. windows / msvc
   haven't seen it compile even once. hiredis on msvc is its own mess. idk how much i care about windows vs just saying linux-only for now.

6. simd dispatch (#12)
   doing real runtime cpu detection + target attributes per compiler (gcc/clang vs msvc) is new territory for me. easy to get something that compiles fine and then crashes on someone else's cpu.

7. the big picture
   the actual "llm gateway + semantic cache" part doesn't exist yet and it's the whole point of the project. i've been fixing plumbing. need to decide the design: which llm api(s) to proxy, where embeddings come from (call an api? local model?), what similarity threshold counts as a cache hit, how to store vectors (in memory? redis?).
